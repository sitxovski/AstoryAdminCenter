# Админ-центр Astory

Одно место для администрирования игры. План и архитектура всех волн — `Docs/Port/plan/ADMIN_TOOL_PLAN.md`.
Сейчас готова **волна А0**: каркас, вход и роли, журнал действий, раздел «Состояние», карточки учётки и персонажа
**только на чтение**, лента по всем журналам, след предмета.

## Где и как открыть

* Панель: **https://@@ASTORY_SERVER_VPN_IP@@:17890/** (VPN), **https://@@ASTORY_SERVER_LAN_IP@@:17890/** (домашняя сеть),
  **https://@@ASTORY_SERVER_WAN_IP@@:17890/** (снаружи — если на роутере проброшен TCP 17890 на @@ASTORY_SERVER_LAN_IP@@).
  Служба слушает все интерфейсы сервера (решение владельца 16.11.2026), только по HTTPS. Сертификат самоподписанный.
  **Поставьте его на свои устройства**, иначе подмену сертификата не отличить от обычного предупреждения браузера.
  Файл: `deploy/asda_admin_center.crt`, SHA-256 EC:3A:D4:9F:4D:84:C2:46:6A:DA:DA:4D:DD:64:58:2C:D5:62:BE:6D:01:B8:CB:C2:99:14:81:8F:BD:2E:F4:3F.
  Как поставить на Windows: двойной щелчок по файлу → «Установить сертификат» → «Текущий пользователь» → «Поместить
  все сертификаты в следующее хранилище» → «Доверенные корневые центры сертификации». После этого браузер не предупреждает.
  Если он предупредит снова, это подмена: не входить.
* Доверенная сеть — только VPN (Tailscale) и сам сервер. Снаружи VPN, включая домашнюю сеть, вход для любой роли
  только со вторым фактором; на каждый логин не больше 12 попыток за 10 минут. Предел попыток и соединений из
  интернета не отрезает вход из VPN.
* Вид — как окна игры: рамки, заголовки, кнопки, вкладки, ячейки и значки вырезаны из атласов клиента
  (`tools/build_skin.py` → `web/skin/`, пересобирать после правок JuiSkin.ini), шрифт Arial с обводкой.
* Первый вход: создать себе пользователя-владельца с ПК (нужен ключ SSH сервера — тот же, что у остальных инструментов):

  ```
  python AstoryAdminCenter\asda_admin.py user-add <логин> --role owner
  ```

  Пароль спросит дважды. При первом входе в панель — включить второй фактор (раздел «О себе»: секрет вводится в
  приложение-аутентификатор вручную, затем текущий код).
* Остальных пользователей владелец заводит в разделе «Пользователи панели».

## Роли

| Роль | Что видит и может |
|---|---|
| владелец (owner) | всё; пользователи панели; откат записей журнала; второй фактор обязателен |
| администратор (admin) | всё, кроме пользователей панели и отката; второй фактор обязателен |
| GM (gm) | состояние, игроки, лента, след предмета, IP/MAC и связанные учётки |
| поддержка (support) | то же, что GM, без IP/MAC и раздела «входы» в ленте |

Права заданы в одном месте — `core/auth.py` (`PERMS`).

## Разделы волны А0

* **Состояние** — 20 процессов стойки (по пути exe) и их порты, машина (ЦП, память, диски), игроки «в игре» по БД.
* **Игроки** — поиск по логину, номеру учётки, имени персонажа (в том числе удалённого), IP и MAC; карточка учётки
  (персонажи, склад, блокировки, премиум-валюта gp7, входы и связанные учётки, соулмейт, удалённые персонажи,
  лента); карточка персонажа (сводка, сумки с иконками и подробностями предмета, почтовый ящик и лоты аукциона,
  навыки, питомцы, друзья, лента).
* **Лента журналов** — все таблицы `joylog1` со столбцом игрока (230 из 247), каталог строится по метаданным базы.
* **След предмета** — по серийному номеру через все журналы со столбцом Serial/Uuid (192 таблицы) + где он сейчас.
* **Журнал действий** — кто, когда, откуда, что сделал; откат обратимых действий.
* **О себе** — пароль и второй фактор.

⚠ Пока игрок в игре, GameServer держит персонажа в памяти — карточка показывает последнее сохранённое в БД.

## Устройство

```
asda_admin.py          точка входа: serve | user-* | status | find | audit | ref-build | selftest
core/                  config, db (подключения, «только чтение», перекодировка Arabic↔cp1251), auth (пароли,
                       второй фактор, сессии, роли), audit (журнал), ops (операция: preview → apply → verify → undo),
                       hostshell (PowerShell на сервере: локально или по SSH)
domains/               status, players, feed, refdata (справочники), panel_users (пользователи панели)
api/server.py          HTTP-служба на стандартной библиотеке (на сервере нет FastAPI — и не нужен)
web/                   панель (без библиотек; данные через /api)
sql/                   01 база+логин, 02 схема adm, 03 права, 10 проверка прав, 99 откат
data/ref/              справочники предметов, иконок, классов, карт, навыков, питомцев (tools/build_ref_data.py)
tests/selftest.py      самотест: без сети (LocalDB) и --live (живые базы, только чтение)
deploy/                выкладка на сервер и обёртка службы
```

**База `AsdaAdmin`** (своя, на том же SQL Server): `adm.users`, `adm.sessions`, `adm.audit`.
**Логин `asda_admin`**: в игровых базах только `db_datareader` (запись невозможна правами), в AsdaAdmin — точечные права;
журнал — только дописывание. Пароль логина — только в `@@ASTORY_SERVER_ROOT@@\AdminCenter\secrets\asda_admin.ini` на сервере
(права: Administrators и SYSTEM). `devgsaccount` служба не использует.

**Служба** на сервере: задача планировщика `AsdaAdminCenter` (при старте машины, от SYSTEM) → `run_service.bat` →
`asda_admin.py serve`; журнал — `@@ASTORY_SERVER_ROOT@@\AdminCenter\logs\service.log`. Брандмауэр: TCP 17890 с любых адресов (служба — только HTTPS).

## Обслуживание

```
python AstoryAdminCenter\asda_admin.py selftest            # без сети: проверки на временных базах SQL Server LocalDB
python AstoryAdminCenter\asda_admin.py selftest --live     # + живые базы под asda_admin (только чтение)
python AstoryAdminCenter\asda_admin.py ref-build           # после выпуска с новыми предметами → потом выкладка (нужны AstoryClient\RawAssets и данные клиента)
python AstoryAdminCenter\deploy\deploy_admin_center.py     # выкладка (самотест → архив → SQL → служба → проверка)
python AstoryAdminCenter\asda_admin.py user-reset-totp <логин>   # потерян телефон
```

На публичном клоне: самотесту нужен LocalDB; проверки, которым нужны файлы рабочей среды автора (`sql/adminc_99_rollback.sql`,
`AstoryServer\Docs\SQL`, `AstoryClient\RawAssets`, Docs, Releases), идут как SKIP. Без LocalDB — выкладка с `--skip-selftest`.
`ref-build` без `AstoryClient\RawAssets` не работает — справочники `data/ref` в репозитории уже собраны.

Откат установки целиком: `schtasks /Delete /TN AsdaAdminCenter /F`, `netsh advfirewall firewall delete rule
name=AsdaAdminCenter`, удалить `@@ASTORY_SERVER_ROOT@@\AdminCenter`. Скрипта отката SQL (`adminc_99_rollback.sql`) в публичном
репозитории нет: база панели — `DROP DATABASE AsdaAdmin`, логины `asda_admin` / `asda_ops` / `asda_bridge` / `asda_reports` — `DROP LOGIN`,
объекты `adm.*` в игровых базах — по списку из `sql/adminc_*.sql` (`sqlcmd -S lpc:.\SQLEXPRESS -E`). Ссылки на `adminc_99` в
комментариях `sql/*.sql` относятся к этому скрипту рабочей среды.

## Дела античита (А6.7, `domains/cases.py`)

Дела AC-NNNN ведёт тот же код `AstoryServer/Tools/Anticheat/ac_case.py` (на сервере — копия `ext/anticheat` с md5 манифеста). Доказательства лежат в
`@@ASTORY_SERVER_ROOT@@\AdminCenter\cases`: права только SYSTEM и Administrators, выкладка папку не трогает. Блок по делу ставит `account.block`, снятие —
`account.unblock`. Откат этих записей из журнала действий запрещён: снимается только через дело (`case.lift`). Права:
- `ac.case` (gm и выше) — открыть дело, приложить доказательства, выгрузка, отчёт отката;
- `ac.decide_low` (gm и выше) — решение ступеней 0–2, его исполнение и отзыв;
- `ac.decide` (admin, owner) — решение со ступени 3, снятие блока, закрытие;
- `ac.appeal` (admin, owner) — апелляция.

Дела служебных учёток (номер до 5000) ведёт только owner. Консоль (`asda_admin.py cases …`) действует только от имени учётки панели:
`--as <логин>`, роль берётся от этой учётки.

**Ограничение.** «Апелляцию пересматривает другое лицо» сверяется по учётке панели. Если у одного человека две учётки панели, это не
различается: атрибута «лицо» у `adm.users` нет. Выдавать одному человеку больше одной учётки панели нельзя.

## Жалобы игроков (А6.11, решение владельца №6 — канал жалоб = бот Discord; `domains/reports.py`)

Игрок подаёт жалобу командой `/report` бота Oracle (`AstoryAdminCenter/DiscordBot`, работает на ПК владельца): категория (чит / бот,
мошенничество, оскорбления, RMT, другое) и до 3 скриншотов — параметрами команды, ник, «когда», описание и ссылки Discord — в окне формы.
Подтверждение с номером видит только автор. Бот пишет жалобу в базу панели `AsdaAdmin` логином `asda_reports`, у которого есть только
EXECUTE на четыре процедуры `adm.Report*` (`sql/adminc_23_reports.sql`); пределы частоты и проверка картинок — в процедурах. Пароль логина —
одной строкой в `@@ASTORY_SERVER_ROOT@@\AdminCenter\secrets\reports_bot.ini` (кладёт выкладка), бот читает его по SSH.

Раздел «Жалобы игроков» (`#/reports`): очередь (новые / в работе / закрытые), карточка (описание, скриншоты, ссылки, автор ↔ учётка игры,
цель — ник → персонаж и учётка, другие жалобы на ту же цель и от того же автора, переходы в ленту журналов, античит и дела учётки) и
действия — `report.take` (взять), `report.close` (закрыть с итогом), `report.case` (связать с делом; «Открыть дело» — форма `case.open`,
предзаполненная жалобой), `report.reply` (ответ автору: бот на ПК раз в минуту отправляет его личным сообщением; автоответов нет).
Права: `reports.view` и `reports.handle` — owner, admin, gm. Консоль: `asda_admin.py reports list|show|take|close|case|reply` (действия — с
`--as <логин панели>`). Пока бот не перезапущен с новой версией, команды `/report` в Discord нет и ответы не отправляются (лежат в очереди).

## Журнал чата и заглушки (А6.12, решение владельца №5 — журнал + заглушка, 90 дней; `domains/chatlog.py`)

Журнал пишет сервер: P129 (AsdaPatch v86) на трёх GameServer кладёт каждое сообщение игрока в `joylog1.chat.message`
(`AstoryServer/Docs/GameServer/chat-log-p129.md`, схема — миграция `chat_01_migrate.sql` рабочей среды; в публичном AstoryServer её нет). Пока P129 не выложен, схемы `chat`
нет — раздел показывает «журнал чата не установлен (P129, AsdaPatch v86 — ждёт общего рестарта)», без ошибок.
Раздел «Журнал чата» (`#/chat`): состояние (строк, первая и последняя запись, режим P129 по копиям), поиск — даты ГГГГММДД, каналы 1…10,
учётка (и сессии, и хозяин персонажа), персонаж, подстрока текста (без учёта регистра; без учётки и персонажа — окно ≤ 31 суток, ≤ 12 поисков
в минуту на пользователя), карта, сервер, отметка заглушки, сырые байты `text_raw` с прочтениями cp1251 / UTF-8 / cp1256; переходы в карточку
учётки и персонажа, «Античит» учётки, жалобы на персонажа, дела учётки; из жалобы, дела и карточки учётки — «Сообщения в чате».
Заглушки: список (действуют / истекли / сняты), `chat.mute` (учётка или персонаж, срок, причина обязательна; `chat.UP_ChatMuteSet`) и
`chat.unmute` (`chat.UP_ChatMuteLift`); откат в «Журнале действий» (снять поставленную / поставить снятую снова на остаток срока). Сервер
перечитывает заглушки раз в 15 с; при Mode=0 P129 сообщение уходит и только помечается в журнале. Права `chat.view`, `chat.mute`,
`chat.unmute` — owner, admin, gm; служебные учётки ≤ 5000 — только owner. Логин `asda_ops` — только EXECUTE двух процедур и SELECT
`chat.mute` (`sql/adminc_24_chat.sql`; без схемы выдача пропускается, её делает следующая выкладка панели или `deploy_p129.py` после SQL).
Консоль: `asda_admin.py chat log|mutes|mute|unmute|undo` (действия — с `--as <логин панели>`).

## Выпуски: статус (А7.1, решение владельца А7 №6 — панель только показывает, выпуск делается батниками DEPLOY на ПК; `domains/releases.py`)

Раздел «Выпуски» (`#/releases`, право `releases.view` — owner, admin) — только чтение, кнопок выпуска нет.
- **Снаружи** служба сама читает с `https://@@ASTORY_UPDATE_HOST@@` `keys/keyring.json`, `channels/alpha.json`, `channels/launcher.json`,
  `version.json`: версия, seq, `min_version`, прошлая версия, срок подписи. Предупреждение «продлить» — за 14 суток, «срочно» — за 3
  (срок 90 суток от выпуска или `6_Resign`; просроченный указатель лаунчер не отвергает, а только пишет предупреждение). Подпись
  проверяется как у лаунчера: корень, вшитый в лаунчер (`Launcher/src/Config.h`), → keyring → неотозванные ключи → конверт; Ed25519 —
  на чистом Python (на сервере нет `cryptography`). Нет keyring — «подпись не проверена». Как у лаунчера, канал в нагрузке должен совпадать с
  именем файла (`version.json` — только alpha), иначе «НЕ сошлась»; keyring на сервере старше, чем на ПК, — предупреждение «откат keyring».
  Перенаправления запрещены; при пустом кэше сервер обновлений читает один запрос, остальные ждут его итог (ревизия 74).
- **С ПК** — снимок, который присылает консоль ПК: `python AstoryAdminCenter\asda_admin.py releases push` (операция `release.push`,
  право `releases.push` — owner; её же можно поставить заданием ПК). В снимке: `releases.log` (30 последних), `Build\EAC\latest.json`,
  Inbox, итоги последних прогонов `DEPLOY\Patch\Logs` и `DEPLOY\Build\Logs`, ключи «есть / срок» и подписанное на ПК. Ключей, путей и
  содержимого закрытых файлов в снимке нет: пути (в том числе с пробелами, в кавычках, X:/ и UNC) заменяются на имя файла, ошибка с
  упоминанием секретов скрывается, перед записью — проверка утечек (пути, \Users\, имя пользователя Windows, домашняя папка, .ssh, .dpapi,
  пароль); найдено — снимок не пишется. Пишется в `AsdaAdmin.adm.ReleasePcStatus` (`sql/adminc_26_releases.sql`) логином `asda_admin` по VPN,
  кто прислал — «cli@машина» (без имени пользователя). Остаток срока подписанного на ПК досчитывает служба, поэтому тот же снимок второй раз
  — только отметка «ПК присылал». Служба раз в сутки (01:10, `release.prune`) оставляет 100 последних снимков (`adm.ReleasePcPrune`, прямого
  DELETE у `asda_admin` нет). Снимок старше суток — пометка «данные ПК устарели». Пока задачи планировщика на ПК нет, снимок отправляется
  только вручную.
Консоль: `asda_admin.py releases show | push [--dry]`.
